# Changelog

All notable changes to Sculk Sight are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

The project is in its proof-of-concept phase, whose single objective is to prove the solver is correct — that the shape the mod draws is the shape the game actually uses. Both exit criteria for that phase are now met; see Verified below.

## [0.0.1] - 2026-09-01 - proof of concept

**Published as a GitHub release only, and marked as a pre-release there.** The jar is `sculksight-0.0.1+26.2.jar`, built from this repository's `dev` branch with `gradlew clean build` on JDK 25, and attached to the tag `v0.0.1`. It is deliberately not listed on Modrinth or CurseForge: those pages, and the logo and icon they require, belong to the next phase, and a GitHub release needs none of them. What it does need is honest release notes about a build that draws one sensor at a time, with no automatic invalidation and no configuration, and those are on the release itself.

Publishing it is what made the versioning scheme due, and it was decided the same day rather than left implicit: **SemVer 2.0.0 core with the target Minecraft version as build metadata**, `MAJOR.MINOR.PATCH+MC`. The core tracks changes to the mod and the metadata tracks the game, so rebuilding unchanged mod code for a later game version is `0.0.1+26.3` rather than a new mod version. That distinction matters here because the manifest's version bound lives inside the jar, so a per-game-version rebuild always changes the jar even when no mod code has changed. Fabric API itself ships under this format.

The tag stays `v0.0.1`: under SemVer's own rules build metadata is ignored for comparison, so `0.0.1` and `0.0.1+26.2` are the same version and the suffix makes the target explicit rather than correcting anything. The pre-release flag on GitHub, not the number, is what marks this as a proof of concept.

No code changed for this release. The itemised entries below are left under `[Unreleased]` rather than moved up under this heading, because they describe the whole of the proof-of-concept phase's development and are not usefully split at this tag.

## [Unreleased]

### Added

- **The Fabric development environment for Minecraft 26.2**, at `fabric/`, derived from the official `fabric-example-mod` template (branch `26.2`). It builds the mod jar, generates decompiled Minecraft sources, and launches a dev client with the mod loaded. There is no mappings configuration, because 26.2 is unobfuscated — see the README's "About mappings" section. Toolchain versions were each looked up against Fabric's own sources rather than recalled, and are listed in the README.
- **`LICENSE` at the repository root**: GPL-3.0-or-later. The `jar` task packages it into the built jar.
- **`README.md` at the repository root**, covering what the mod does, what it does not do yet, the requirements for a player, and the build and development setup.
- **The client entrypoint** `com.scr0ols.sculksight.client.SculkSightClient`. It logged one line and did nothing else; it existed so the toolchain could be verified end to end before any mod code depended on it.
- **The solver.** `WorldView`, `Face`, `PositionFilter`, `DetectionSet`, `OcclusionTest`, `ShellSolver`, `BoundaryFaceSink` and `BoundaryFaceExtractor`, in `com.scr0ols.sculksight.solver`. The package names no Minecraft class at all — it reaches the world through the narrow `WorldView` interface, which is what makes it testable from a plain JVM test and portable to a second mod loader later. The solver runs synchronously; the threading model it is designed for is not implemented, because without a renderer there is nothing for a worker to hand off to.
- **The differential verification harness**, in `com.scr0ols.sculksight.verify`: `SensorProbe`, `Reaction`, `Outcome`, `VerificationSample`, `VerificationReport` and `DifferentialVerifier`. Everything above the probe seam was complete and tested before the probe itself existed, since how a vibration is triggered and observed was still an open question at that point.
- **JUnit on the Fabric build** (Jupiter 6.1.3 via `org.junit:junit-bom`), test scope only, with the version looked up on Maven Central rather than recalled.
- **The `WorldView` implementation over a real level**, `com.scr0ols.sculksight.client.LevelWorldView`. It takes a `BlockGetter` rather than a `ClientLevel`, because the vanilla segment test it delegates to is a `default` method on that interface. This is the only class in the mod that names the vibration-occlusion block tag.
- **The differential verification probe and command**, `com.scr0ols.sculksight.verify.IntegratedServerSensorProbe` and `VerificationCommand`. `/sculksight-verify <scene> [samples]` aims at a sculk sensor, solves against the **client** level, probes against the integrated server's level, and reports disagreements. It is registered only when `FabricLoader.getInstance().isDevelopmentEnvironment()` is true, and reaching server-side state is a development-environment concession that the shipped mod does not make — the dev-only gate is what keeps the client-side design honest.
- 39 unit tests covering the six-ray occlusion rule, the detection set, the solver, boundary-face extraction and the verification harness.
- **The renderer.** `ShellStyle` and `ShellQuad` in `com.scr0ols.sculksight.mesh` on the main source set, `ShellMeshBuilder` beside them on the client source set, and `ShellPipelines`, `SensorKey`, `ShellStats`, `ShellEntry`, `ShellUploadSlot`, `ShellBuffer` and `ShellRenderer` in `com.scr0ols.sculksight.client`. Aim at a sculk sensor and press **K**: the mod derives the radius through `GameEventListener.Provider`, solves, encodes one quad per boundary face into a sensor-relative mesh, uploads it once, and draws it twice per frame from that one buffer — a see-through pass with no depth test at α 0.10, then a depth-tested pass at α 0.25. Pressing again clears it. The key binding goes through Fabric's `KeyMappingHelper`, so it appears in the vanilla controls screen and can be rebound even though this version has no config of its own.
- **Only boundary faces are drawn** — one quad only where the neighbouring position is outside the set. That turns tens of thousands of positions into hundreds of quads, and it is also what makes the shape readable: the notch that wool carves out of the region is visible precisely because the shell has a surface there.
- **The see-through pipeline is built by the mod and ships no shader asset**, from `RenderPipelines.DEBUG_FILLED_SNIPPET` with the depth state cleared and its own identifier, naming vanilla's `core/position_color` on both stages. Both passes inherit their bind-group layout and their shader from that one snippet, which is a correctness requirement rather than tidiness: uniform blocks are matched **by name**, and a mismatch fails silently — the geometry draws in the wrong place with no error at all.
- **The drawn shell is checked against the solver's output rather than eyeballed.** Every boundary face is one quad and every quad is four vertices, so the face count `BoundaryFaceExtractor` produces and the vertex count `BufferBuilder` produces are related by an exact factor of four. `ShellRenderer` asserts that before uploading and **refuses to draw** when it fails. That is the project's governing principle applied literally: a shell that does not match the solver is the wrong shape, and drawing the wrong shape is worse than drawing nothing. Each solve also reports its predicted, occluded-out and boundary-face counts to chat, so a shell and a `/sculksight-verify` run on the same sensor print directly comparable numbers.
- 29 further unit tests, for the shell's quad geometry and the style, bringing the suite to 69. `ShellQuad` and `ShellStyle` are deliberately free of Minecraft types and live on the main source set, so the part of the encoder that can put the shell in the wrong place is reachable from a plain JVM test; `ShellMeshBuilder` names `BufferBuilder` and `MeshData` and cannot be.
- **The shell is more opaque when you are standing inside it.** It was not an illusion. The shell's faces are drawn from both sides, so looking at it from outside your view crosses the near wall and the far wall, two translucent layers; from inside, the near wall is behind you and only one layer is left, which is close to half the coverage. Each pass now corrects for that when the camera is inside the detection volume, so the shell looks the same from either side. Inside is tested against the detection set rather than against the radius, so standing in the shadow of a wool wall correctly counts as outside.
- **The shell knows where its own creases are**, the edges where its surface turns rather than every edge between two blocks. That is the seam an occluding block carves, and it is computed and tested but not currently drawn: an outline over it was built and then taken out again after it was seen in the game, because at any distance it read as a black grid over the shape rather than as a highlight on it. What it is for is a narrower outline later, over the carved seam alone.
- 20 further unit tests, for the crease rule over all sixteen of its cases, the crease sweep, the edge geometry and the new opacity arithmetic, bringing the suite to 89.
- **The mod can now say how long its own work takes**, which it could not before: it reported how many positions and faces a shell had, and nothing about time. There are two numbers, and they are the two the performance targets are written against. Per solve, the mod prints how long it spent solving and building the mesh, how long the upload of that mesh took, and the sum. Per shell, when you switch it off (and every ten seconds while it is on), it prints how many frames it drew, the smallest, average and largest time one of those draws took, and how many of those frames went over the target. Both go to chat and to the log, alongside the counts that were already there.
- **The timing is off in a normal game and takes a deliberate step to turn on.** It runs by itself in a development environment, and in an ordinary installation only if the game is launched with `-Dsculksight.timing=true`. When it is off nothing is allocated and no clock is read, which matters because one of the two numbers is measured once per frame. What it measures is processor time: the per-frame number is the cost of preparing the draw, not of the graphics card carrying it out, so a number under target says the processor side is under target and says nothing about the card.
- **The timing lines are also written to a file**, `sculksight-timings.txt` in the game folder, so they can be copied instead of read off the screen. It is the same text the chat shows with the time of day in front of it, one dated block per launch, written a line at a time so the file can be opened while the game is still running. It appears only when timing is on, and a folder that cannot be written to costs one error line rather than one per solve.
- 8 further unit tests, over the arithmetic behind what a timing report says and what a written line looks like, bringing the suite to 103. They are the first tests here over a client-side class, and the reason they are possible is that the switch deciding whether timing runs at all lives in a class of its own: reading it needs a launched game, and everything that decides what the numbers say does not.
- **Automatic sensor discovery.** The mod now keeps its own index of every game-event listener in a loaded chunk (position and radius, radius read once when the entry is added), maintained by block placement, breaking, and chunk loading and unloading, with nothing swept on a timer or a frame. This is the enumeration surface every mode past the one you are aiming at needs.
- **Mode C: are you detected?** Press **J** to turn it on. Every tick, the mod checks your current position against every sensor the index knows about (in range, and not blocked by anything between you and it, the same two checks a shell is built from) and says in chat when that answer changes: it does not repeat itself while nothing has, and it draws nothing in the world. Press **J** again to turn it off. This runs independently of the shell mode A draws; both can be on together.
- 6 further unit tests, for the range and occlusion checks mode C runs, bringing the suite to 109.
- **Mode C can now be checked against the game, the same way the shell already could.** A second development-only command, `/sculksight-verify-detection <scene> [samples] [seed]`, aims at a sensor and asks the game directly whether it agrees with mode C's own answer about each of a few hundred sampled positions. It is the same machinery the existing `/sculksight-verify` uses below the surface (the same sampling, the same way of triggering a vibration and watching for the reaction, the same report), pointed at a different one of the mod's answers, because mode C works out detection with its own code rather than by building a shell. Neither command exists in a built jar. What this checks is the geometry: whether a position is in range and unblocked. It does not check that the mod's list of nearby sensors is complete, and that limit is written down rather than glossed over.
- 11 further unit tests, over the new scan and over the range check it now shares with mode C's own detection, bringing the suite to 120. Two of them assert that mode C's answer and the shell solver's answer agree position for position over the same world, in open air and with occlusion, so the two can no longer drift apart without the build failing.
- **The sensor index can now be checked against the world too, not only mode C's geometry.** A third development-only command, `/sculksight-verify-index <chunkRadius>`, sweeps every game-event listener within the given number of chunks of the player directly - built without going through the mod's own index at all, so a bug in that index cannot also hide from the thing checking it - and compares the result against what the index itself currently holds nearby. Where the geometry commands ask "is this position in range and unblocked", this one asks "does the index's list of sensors and radii actually match what is out there right now", which catches a different class of bug: a sensor the mod's index missed, or one it never noticed disappear, either of which would otherwise look exactly like "you are not detected" whether or not that was true. It checks every listener within range rather than a sample, since comparing two in-memory lists costs nothing like asking the live game does. This command has not been run yet.
- 8 further unit tests, over the comparison the new command runs, bringing the suite to 128.
- **A NeoForge module, `neoforge/`, builds a bare client-only mod jar for the first time.** `com.scr0ols.sculksight.neoforge.SculkSightNeoForge` logs one line on client setup and does nothing else, which is deliberate: it proves the toolchain end to end (build.gradle, `neoforge.mods.toml`, the loading class) rather than porting any of the mod's actual behaviour, the same bar the Fabric side cleared at the very first entry in this file. NeoForge and Minecraft versions (`26.2.0.75` and `26.2`) were read from the official `MDK-26.2-ModDevGradle` template and from `maven.neoforged.net`'s own version metadata on 2026-09-04, never recalled — Minecraft 26.2 postdates any assistant's training data the same way it did for Fabric's own toolchain. The build mechanism this needed is under Changed, below.
- **NeoForge now registers a real shell (mode A) and a real detection indicator (mode C), not a bare mod.** `SculkSightNeoForge` wires `RegisterKeyMappingsEvent`, `ClientTickEvent.Post`, `RenderLevelStageEvent.AfterTranslucentBlocks`, `ClientStoppingEvent`, and `LevelEvent`/`ChunkEvent`'s `Load`/`Unload` to the same loader-independent logic Fabric's own `SculkSightClient` now calls into, both read from real NeoForge/FancyModLoader source rather than assumed. The split surfaced one real difference between the loaders: NeoForge has no block-entity-specific load/unload event, so `SensorIndex` on NeoForge falls back to a per-chunk sweep alone, a narrower guarantee than Fabric's own — a sensor placed into a chunk that is already loaded was not picked up there until that chunk reloads (closed under Fixed, below). Not wired at this point: the three dev-only verify commands, which followed shortly after.
- **A settings screen, and a settings file underneath it that the mod owns.** Open it from Mod Menu on Fabric or from NeoForge's own mod list. There is one setting: how solid the shell looks, as a percentage. It moves both of the shell's two passes together, keeping the proportion between them that the see-through pass was designed at, so one slider does not let the ghost half end up denser than the solid half it sits under. Zero is allowed, for a player who wants the detection indicator without anything drawn in the world. Saving takes effect immediately: the shell you have up is dropped and comes back at the new setting on the next keypress.
- **The file is `config/sculksight.json`, and it is meant to be readable.** It is written indented, one flat object, with whole numbers written as whole numbers rather than as `25.0`. A player without Mod Menu can edit it by hand and get the same result the screen would give, which is the point of the mod owning the format rather than borrowing one.
- **A settings file that has been damaged never stops the game, and is never quietly rewritten.** A file that is missing is an ordinary first run. A file that cannot be read or parsed, or that gives a setting the wrong kind of value, falls back to the settings the mod ships with, says so in the log, and **leaves the file exactly where it is**: it is the only copy of what was typed, and it is not overwritten until something is saved over it deliberately. A setting that is merely missing, or a number outside the allowed range, is repaired rather than treated as damage, and each repair is one line in the log rather than a silent correction. A key the mod does not recognise is left alone, so a file from a later version, or one carrying a note, still loads.
- **Saving writes to a temporary file and then moves it into place**, so an interrupted save leaves the old file rather than half of a new one.
- **The JSON reader and writer are this mod's own**, about four hundred lines in `common`, reachable from the test suite where a library on Minecraft's own classpath would not have been. It reads all of JSON and none of the informal extensions: a comment, a trailing comma or an unquoted key is an error with the offset it happened at, rather than something quietly tolerated.
- **NeoForge has its own language file for the first time**, so its key bindings show their names in the controls screen instead of raw translation keys.
- 80 further unit tests, over the reader and writer, the schema, the file store against a temporary directory, and the arithmetic that turns one percentage into the two alphas the shell draws with, bringing the suite to 229. Two of them hold the configured shell at its default setting to exactly the appearance the mod shipped with before there was a setting at all, so the two cannot drift apart without the build failing.
- **The shell's colour now depends on which detector was aimed at.** `DetectorType` classifies the targeted block into `NORMAL_SENSOR` (amber `#FFA300`, unchanged), `CALIBRATED_SENSOR` (`#99CCFF`) or `SHRIEKER` (`#8B0025`), and `ShellRenderer` applies that colour on top of the configured style, leaving alpha, face shading, blending and the camera-inside correction untouched. `ShellStyle.withColour` is the one mechanism both the render path and its tests go through.
- **The active shell can show per-block travel delays.** Press **H** while a shell is selected with **K** to place the real tick count at every in-range block position, including air. Labels are depth-tested against the player's view, and sensor-occluded positions use the established purple convention.

### Changed
- **The timing report now says which thread each number came from, and it was wrong before.** When the solve moved to a background thread, the report kept adding the solve's cost to the frame's cost and comparing the total against a per-frame budget — so a solve that cost the frame a fifth of a millisecond was reported as sixteen. The report is now split by thread: the two phases that genuinely happen on the game's thread, the region copy and the buffer upload, are added together and compared against the budget, and the background thread's own cost is printed beside them and left out of that sum. The region copy is also timed at all for the first time; nothing had ever measured it, and it turns out to be about one percent of the budget.


- **The build is now three modules, `common/`, `fabric/` and `neoforge/`, under one root at the repository's own directory rather than at `fabric/`.** This is the standing rule that shared code gets extracted when duplication becomes concrete rather than anticipated, firing at its intended trigger: adding a second loader. Everything with no Fabric dependency — the solver, the mesh records, the verification harness, `SculkSight` itself — moved to `common/` unchanged; `fabric/` keeps its client-side code exactly as it was, now compiled from shared source rather than as its own project root. `common/` gets its Minecraft classpath through ModDevGradle's NeoForm-only mode, and each loader module compiles the shared sources directly into its own build rather than depending on a published jar. Architectury was considered and deliberately not used: the two loaders' Minecraft artifacts are not the same binary even though both carry 26.2's Mojang names, and compiling the sources twice is what keeps each side honest about that.
- **`common` gained a second source directory, `src/client/java`, and the nine Fabric-client classes that mixed loader API into loader-independent logic are split.** `ShellRenderer`, `SensorIndex` and `DetectionIndicator` now expose public static handler methods over vanilla types; `TimingGate`/`TimingLog` read a small `Environment`/`ClientPlatform` seam instead of `FabricLoader` directly; both `fabric/`'s `SculkSightClient` and `neoforge/`'s `SculkSightNeoForge` are now pure registration hubs. That second directory is exposed to each loader as a source directory rather than ever compiled by `common` itself, and the reason is mechanical: the render-pipeline snippet the shell's see-through pipeline is built from is private-access under a bare Minecraft classpath with no loader attached, even though both real loaders compile it without complaint.
- **The Fabric jar's own version and file name are unchanged** (`sculksight-0.0.1+26.2.jar`); the restructuring moved where its sources live, not what it builds.

- **The shell's colour loses its blue component: `#FFA33C` becomes `#FFA300`, and this came out of measuring a screenshot rather than judging one.** The shell had been reported as looking washed out and cloudy next to a third-party sphere overlay drawn over the same region. Both were in one frame against the same water, which makes each one's composited opacity solvable from the pixels: a rendered pixel is the source colour and the background mixed in the proportion the compositing produced, so the proportion follows. The two came out at 0.55 and 0.54, meaning **they were already the same density and opacity was never the difference**. Solving the overlay's own colour out of its pixels gave a red-to-green ratio of 1.58 against this mod's 1.56, so the hue was not the difference either. What was left was that this mod's amber carried 60 units of blue and the overlay's colour carried none, and at that opacity against a blue-green background roughly half of that blue survives into the result and lands on top of the blue the background already contributes. That is what turned gold into pale tan. Removing it keeps the hue exactly where it was and makes the colour do better the job it was picked for, since amber was chosen in the first place for being the opposite of the Deep Dark's blue-teal.
- **The directional shading is stronger: the per-face multipliers widen from 1.00 / 0.92 / 0.86 / 0.80 to 1.00 / 0.86 / 0.78 / 0.66**, top face to bottom face. The same measurement showed the original deltas producing almost no variation across the shell's interior, so the faces read as one mass rather than as the carved surface that is the whole point of drawing boundary faces. Shading still multiplies colour and never opacity, which is what keeps the total coverage a view ray accumulates dependent only on how many faces it crossed. The cost is stated rather than found later: the interior of this shell already varies more than the overlay's does, because the voxel staircase hands different rays different numbers of faces to cross, and stronger shading adds to that. Making the interior genuinely calm would need the fill to write depth, which is a much larger change and is not made here.
- **The two opacity values are unchanged, and are now confirmed rather than only reasoned.** The see-through and depth-tested passes were derived from an argument about how many translucent layers a ray crosses through a shell whose back faces are drawn. That argument predicted a composited opacity of 0.544 and the screenshot measured 0.557, which is the first time the model behind these numbers has been checked against the screen instead of against itself.
- **All three of the above were then looked at in the running game and kept.** The shell reads as the shape it is meant to be, and the boundary an occluding block carves out of it is legible without any outline drawn over it, which is what the shorter-lived crease-edge outline had been added and then removed trying to achieve.

- **The renderer's Fabric hook is `LevelRenderEvents.AFTER_TRANSLUCENT_TERRAIN`**, chosen because it fires inside `LevelRenderer`'s main frame-graph pass: the camera matrix is on the model-view stack, terrain and its depth are complete, and clouds, weather and the post-processing chains have not run.
- **The solve runs on the client thread, not on a worker.** The worker-to-render hand-off is built and used exactly as designed — the encoder produces a `MeshData`, the producer offers it into `ShellUploadSlot` stamped with a revision, the render callback takes it and uploads — but the producer stays on the client thread, because whether a worker may safely read a live `ClientLevel` has not been established, and this project does not write unverified claims about Minecraft's behaviour into code. Moving the producer later is a change of submission site and nothing above it.
- **`ShellMeshBuilder.build` now takes the `ByteBufferBuilder` it encodes into as a caller-owned parameter, instead of allocating and closing one of its own.** See Fixed below for why.
- **Fabric Loom is pinned to the released `1.17.20`** rather than the template's `1.17-SNAPSHOT`, so that two checkouts of the same commit resolve the same plugin.
- **`ShellSolver.solveDetailed(...)` (both overloads) now returns `ShellSolution`**, pairing the accepted `DetectionSet` with a second `DetectionSet` of the positions the six-ray occlusion rule excluded. `ShellSolver.solve(...)`'s existing signatures are unchanged and now delegate to `solveDetailed(...)`, discarding the occluded-out half; no extra ray is cast either way.
- **`DifferentialVerifier.verify` stratifies its sample three ways instead of two.** It takes a `ShellSolution` rather than a plain `DetectionSet` and splits the sample across the new `PredictedClass` enum (`IN_SET` / `OCCLUDED_OUT` / `OUT_OF_RANGE`), so occluded positions get a dedicated share instead of being diluted into a much larger "everything else" bucket. A class smaller than its share is backfilled from the other two, so the fix costs no sample volume elsewhere. This matters because occlusion is the interesting half of the mod and the old split barely tested it — see Verified below.
- **`VerificationSample` carries a `PredictedClass` instead of a `predictedInSet` boolean**, and `VerificationReport` gained `inSetSampled` / `occludedOutSampled` / `outOfRangeSampled` counts, printed in `summary()`.
- **`/sculksight-verify <scene> [samples] [seed]`**: the seed is now an optional third argument, defaulting to the sensor's packed block position exactly as before when omitted, so a scene can be resampled at fresh positions without moving the sensor.
- **The mod version is now `0.0.1+26.2`** rather than `0.0.1`, adopting the versioning scheme described under `[0.0.1]` above.

### Removed

- **The GitHub Actions workflow that shipped with the template.** It assumes the Gradle build sits at the repository root, whereas this project's build sits at `fabric/`, so as shipped it would have been silently inert. CI belongs to the next phase; when it is set up it needs a `working-directory` or a `-p fabric` argument, and it must build every supported loader.

### Fixed

- **The renderer's first live frame crashed the client, and the cause was a resource-lifetime bug in the mesh encoder.** `ShellMeshBuilder.build` allocated its own `ByteBufferBuilder` and closed it in a `try`-with-resources before returning — but the returned `MeshData` is read later, on the render thread, by which point the builder that produced it had already been closed. `ByteBufferBuilder.close()` invalidates every `Result` it ever produced: it frees the native pointer and bumps an internal generation counter that every `Result.byteBuffer()` call checks. So the very first shell built a valid mesh, and the render thread's later read of it threw `IllegalStateException: Buffer is no longer valid`, crashing the client with a `ReportedException`. `MeshData.close()` — which `ShellUploadSlot`'s existing close discipline already calls at exactly the right points — does not free that memory; only the parent `ByteBufferBuilder`'s own `close()` does. `ShellMeshBuilder.build` now takes the `ByteBufferBuilder` as a parameter the caller owns, and `ShellRenderer` holds one long-lived, growable instance closed only when the client stops. This matches how vanilla's own `SectionCompiler` works: it receives its `ByteBufferBuilder`s from a pool it does not own, rather than allocating and closing its own per compile.

- **Speckling where the shell lies flat against a block face.** The shell's surfaces sit exactly on block boundaries, so a shell face flush against the underside of a wool block was at precisely the same depth as that block and the two fought over which one to draw, pixel by pixel. The shell's depth-tested pass now asks to be treated as very slightly nearer than whatever it is flush with, which is the same remedy the game uses for its own outlines. The see-through pass never needed it, since it does not compare depth at all.

- **Mode C's toggle key did not work: it was bound to `L`, which is also vanilla's own default key for the Advancements screen.** The first live test pressed `L` expecting the detection indicator and got the Advancements screen instead, and it turned out the indicator's own toggle had never fired even once in any session, since it was added: every session's log was checked back to when the key existed, and the indicator's own confirmation line, which it prints unconditionally on every toggle, was never once in it. Moved to **`J`**, confirmed working on retest. One thing the investigation did not resolve: the game's own key-binding source reads as though the mod's binding should have registered its click independently of the collision, and why it did not was not traced.

- **On NeoForge, mode C never detected a sensor placed or broken while its containing chunk stayed loaded — reported 2026-09-08 as "pressed J inside the detection box and it said I was no longer in range" and the message never updating between range and not-range.** NeoForge has no live block-entity add/remove event to populate `SensorIndex` from mid-session (the narrower guarantee noted under Added, above), so a sensor built and tested in one continuous session was never indexed at all: every reading came back "not detected", unconditionally, which explains both symptoms as one root cause rather than two. `SensorIndex.reconcile`, backed by the new pure `IndexReconciliation.apply`, now lets `SculkSightNeoForge` resync the index once a second against an independent sweep (`IndexSweep`, the same one `/sculksight-verify-index` uses) for a bounded 5×5-chunk region around the player. Fabric is untouched — its own live block-entity events already cover this. `IndexReconciliationTest` reproduces the missing-entry bug directly and its counterfactual; no graphics stack was available to replay the two symptoms in a live client, so this awaits the captain's own retest.

- **A shell rendered around a sculk catalyst — confirmed in game on Fabric — even though a catalyst does not belong to the sensor family.** `DetectorType.of` fell through to `NORMAL_SENSOR` for any block it did not otherwise recognise, and a catalyst's block entity satisfies `ShellRenderer`'s `GameEventListener.Provider` check for an unrelated reason: it reacts to nearby mob deaths by spawning sculk growth, not by emitting the vibration-frequency detections the sensor family reports. So aiming at one and pressing **K** drew a shell as if it were a plain sculk sensor. `DetectorType.of` now returns `Optional<DetectorType>`, empty for the catalyst and any other non-detector block, and `ShellRenderer` refuses to draw when it is empty.

- **Wool carpet did not dampen a shell the way wool itself does — reported 2026-09-09 during v0.2 tick-overlay playtesting, even though carpet is made of wool.** `LevelWorldView` tested each candidate block against vanilla's `OCCLUDES_VIBRATION_SIGNALS` tag alone, and that tag does not carry wool carpet. Treating carpet as an occluder alongside wool is this mod's own product decision, not a vanilla behaviour it mirrors. The mod's own predicate, `VibrationOcclusion.isOccluder`, now also accepts any of the 16 registered wool-carpet blocks, checked against a `Set<Block>` built once rather than against a fresh list per call, since this predicate runs on the six-ray occlusion hot path once per traversed block. `VibrationOcclusionTest` covers every carpet colour and confirms unrelated blocks are unaffected.

### Notes on what the unit tests do and do not establish

JUnit tests validate the solver against this project's model of Minecraft, not against Minecraft itself. If the model is wrong, the solver, the tests and the oracle are all consistently wrong and all green — which is exactly why the differential verification below exists and is treated as the real gate. The one unit test that owes nothing to anyone's model of the game is the open-air position count, compared against the integer lattice counts of 2 109 at radius 8 and 17 077 at radius 16.

**The first exit criterion is met.** Differential verification was run live on 2026-09-01 against a normal sculk sensor at `x=13, y=108, z=-1`, radius 8:

**What it does not establish, stated because the headline number invites over-reading.** At the time of that run, sampling was stratified in two classes, so only about five of the wool scene's samples are expected to have landed on an occluded position: the run tested the range check two hundred times and the carved shape roughly five. That weakness in the instrument has since been fixed — the sampler now stratifies three ways, and a re-run of the wool scene tests occlusion 67 times.

**The second exit criterion — "the rendered shell matches the solver's output" — is now met.** Run live on 2026-09-01 across the same three scenes, on the OpenGL backend, which is where a threading mistake in the buffer path throws rather than racing silently:

- **open-air and sphere-corner** (same sensor as the differential-verification run above, radius 8): the shell's own reported numbers (`2109` positions in range, `0` occluded out) matched `/sculksight-verify`'s exactly, and both a 200-sample and a 2000-sample verification run against that sensor came back clean with zero disagreements.
- **wool**: closing a 3×3 wool cap over the sensor and then opening a hole in its centre moved the shell's `predicted` and `occluded-out` counts by exactly 14 in opposite directions (1955/154 → 1969/140) and visibly opened a matching notch in the drawn shell. This is the one check that can actually falsify the encoder, since a dropped or duplicated boundary face shows here and not in open air.
- The two-pass compositing reads as intended: the part of the shell with direct line of sight to the camera is visibly reinforced, and in game the detectable/non-detectable boundary corresponds to where the shell is drawn.
- Coplanar shell/terrain faces do speckle (z-fighting), confirmed by eye — a cosmetic artifact, not a criterion failure, and on the list to fix.
